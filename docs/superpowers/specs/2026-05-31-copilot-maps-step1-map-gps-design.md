# Copilot Maps — Step 1: Map + GPS — Design Spec

**Date:** 2026-05-31
**Status:** Approved (design), pending implementation plan
**Author:** Russell (with Claude)

---

## Context

Copilot Maps is an AI navigation app for Android: while driving, the user asks
questions in plain language and a voice copilot answers from live route data.
The full system is decomposed into five sequential sub-projects (per the project
brief): (1) Map + GPS, (2) Routing, (3) Places, (4) Copilot AI agent, (5) Live
navigation. Each sub-project gets its own design → plan → build cycle.

**This spec covers Step 1 only: Map + GPS.**

The developer is an AI/backend engineer with **no prior Android experience**.
This is their first Android app. The Android side is the unfamiliar part, so
Android steps are made explicit. The end goal of the overall project is a Google
Play Store launch.

### Starting conditions

- No Android Studio installed (starting from zero on tooling).
- A **physical Android phone** is available for real GPS testing.
- No Google Cloud account yet (developer has a Gmail account to create one).

---

## Goal & Definition of Done

**Goal:** Prove the Android toolchain works end-to-end by displaying a Google Map
centered on the user's live GPS location.

**Scope decision:** *Static location* (Option A) — show the map with a blue dot at
the user's current location. The "following camera" behavior (map tracks the user
as they move) is explicitly **out of scope** for Step 1 and deferred to a later
step.

**Definition of Done:**

1. The app installs and runs on the real Android phone.
2. It requests location permission with a clear rationale.
3. On grant, it shows a Google Map centered on the user's actual GPS location with
   the my-location blue dot enabled.
4. It handles permission denial without crashing (shows a graceful message + a way
   to grant).

---

## Technical Approach

**UI toolkit:** Jetpack Compose + `maps-compose` (Google's Maps Compose library).
Chosen over the legacy XML Views + `SupportMapFragment` approach because it matches
the project brief, is the current Google-recommended standard, involves less
boilerplate, and carries forward cleanly to later screens (route drawing, copilot
chat panel, voice UI).

**Architecture:** A **single-module** app organized by responsibility, using the
Screen + ViewModel + UiState pattern (unidirectional data flow: events down, data
up).

Deliberately **deferred** until a later step has a concrete need for them:

- **Hilt** (dependency injection) — dependencies are passed manually at this size.
- **Room** (local database) — there is no data to persist in Step 1.
- **Multi-module split** and **convention plugins** — unnecessary for one screen.

Rationale: the full multi-module + Hilt + Room architecture (à la NowInAndroid) is
the right destination for a mature app, but imposing it on a first app's first
screen costs days of Gradle/DI wiring before any pixel appears, with no payoff yet.
The UiState pattern is adopted now because it scales to every later screen; the
heavier infrastructure is introduced later when a real need justifies it.

## Project Structure

```
app/
  src/main/java/com/<pkg>/copilotmaps/
    MainActivity.kt          # hosts the Compose UI, app entry point
    ui/
      map/
        MapScreen.kt         # @Composable: GoogleMap + permission UI
        MapViewModel.kt      # holds location state, exposes MapUiState
        MapUiState.kt        # Loading / PermissionNeeded / Located / Error
      theme/                 # Compose theme (generated by Android Studio)
    location/
      LocationProvider.kt    # thin wrapper over FusedLocationProviderClient
  src/main/AndroidManifest.xml  # permissions + Maps API key reference
  build.gradle.kts           # dependencies (maps-compose, location, etc.)
```

## Components & Data Flow

### Components

- **`MainActivity`** — sets the Compose content to `MapScreen`. App entry point;
  nearly empty.
- **`LocationProvider`** — thin wrapper over `FusedLocationProviderClient`. Single
  responsibility: "give me the current location, once." Returns a lat/lng or an
  error. Testable in isolation.
- **`MapViewModel`** — owns `MapUiState`. On start: checks whether location
  permission is granted. If yes → asks `LocationProvider` for location → emits
  `Located(latLng)`. If no → emits `PermissionNeeded`.
- **`MapScreen`** — observes `MapUiState` and renders the appropriate UI per state.
  Owns the permission *request* UI via Android's official permission launcher
  (`rememberLauncherForActivityResult` with `RequestPermission` contract).

### Flow

`MapScreen` launches → checks permission → (granted) `MapViewModel` →
`LocationProvider` → location flows back up → `GoogleMap` composable centers on it
with the my-location blue dot enabled.

---

## State Model & Error Handling

`MapUiState` is a sealed interface covering:

- **`Loading`** — awaiting permission decision / first GPS fix → spinner.
- **`PermissionNeeded`** — not yet granted, or denied → explain *why* location is
  needed + a button to grant (or to open Settings if permanently denied).
- **`Located(latLng)`** — success → map + blue dot.
- **`Error(message)`** — location services off, no GPS fix, etc. → friendly message
  + retry. If no fix is available, fall back to a default city center so the screen
  is not empty.

**Known first-time gotcha (documented, not a state):** a bad or missing API key
makes the map render as a blank gray grid rather than throwing an error. The
implementation notes will show how to recognize this.

## Environment Setup Sequence

Ordered so a **blank app runs on the real phone before any Google Cloud / Maps
work** — isolating "is the toolchain broken?" from "is the Maps integration
broken?"

1. **Install Android Studio** (bundles the Android SDK, emulator, Gradle).
2. **Create the project** — "Empty Compose Activity" template.
3. **Set up the phone for development** — enable Developer Options + USB debugging,
   plug in, authorize the computer.
4. **First run: blank template app on the real phone** — toolchain checkpoint.
5. **Google Cloud setup** — create a project, enable **Maps SDK for Android**,
   create an **Android-restricted API key**, enable **billing** (required even for
   the free tier; Maps' free monthly credit covers dev volume).
6. **Wire the key in** — via the manifest, sourced from a local properties file
   that is **git-ignored** so the key is never committed.
7. **Add the map** — add the `maps-compose` dependency and the `GoogleMap`
   composable; confirm a map renders.
8. **Add location** — permissions + `FusedLocationProvider`; center on the blue
   dot.

**Note:** Step 5 requires entering a credit/debit card for the Google Cloud
billing account (developer has accepted this), though usage stays within the free
tier.

## Testing

**Manual testing on the real phone:**

- Grant permission → map centers on actual location with blue dot. *(happy path)*
- Deny permission → graceful `PermissionNeeded` message, no crash.
- Turn location services off → `Error` state with retry / default fallback.

**Automated testing:** minimal for Step 1. `LocationProvider` and `MapViewModel`
are structured to be unit-testable (state transitions), but heavy test
infrastructure is deferred along with Hilt/modules. Map rendering is verified
manually on-device.

---

## Out of Scope (Step 1)

- Following / tracking camera as the user moves (deferred).
- Any backend, routing, places, or copilot functionality (Steps 2–4).
- Background location / live navigation (Step 5).
- Hilt, Room, multi-module architecture, convention plugins (introduced when a
  later step needs them).
- Play Store release process (relevant at a later milestone, not Step 1).
